# AGENTS.md: tennis/

Notes for coding agents. The human-facing explanation is in `README.md`.

## What this is
A learning project. A tiny network, TennisNet-lite (3.45M parameters), finds the ball, both players and the 14 court keypoints in broadcast tennis video. The player and court labels were auto-generated by bigger models, so training learns from those labels (distillation). **v2 is the current model** (`runs/lite_v2/best.pt`). v1 is the baseline. The colour variant (v3) was abandoned.

## Code-style rules (important)
- **Readability over cleverness.** People read this code to learn from it. Use short functions, plain names and comments that say *why*. Don't introduce frameworks, configs, class hierarchies or dependencies.
- Keep the `lite/` files numbered as steps in their docstrings ("Step N - ...") and self-contained.
- Grayscale stays the default. `--color` paths must keep working, but they aren't the main path.
- Run on MPS when available, then CUDA, then CPU (the pattern is already in each script).

## Layout
```
setup.sh          venv, dataset download, TennisCourtDetector clone and patch, court weights
label_all.sh      the full auto-labelling and dataset pipeline, in order (read it to see the order)
label_players.py → select_players.py              players  (labels/players.jsonl)
label_court.py → fit_court_clips.py               court    (labels/court.jsonl)
warp_court.py ×2 → fit_court_clips.py → merge_court.py   game4 court fix (patched into labels/court.jsonl)
build_dataset.py  → data/tennis.jsonl + data/meta.json   (one JSON line per frame; schema in its docstring)
lite/             the small model: prepare_frames → data → model → decode → train → demo → evaluate
```
Git-ignored and regenerated by the scripts: `raw/` (TrackNet frames and CSVs), `labels/`, `data/`, `models/` (court detector weights), `runs/` (checkpoints and videos), `third_party/`, `.venv/`.

## Commands (run from `tennis/`, with `.venv/bin/python`)
- Demo: `python lite/demo.py --clip game10/Clip1 [--mode boxes|minimap|both] [--weights ...]`. Output is mp4v. For browsers, convert with `ffmpeg -i in.mp4 -c:v libx264 -pix_fmt yuv420p -crf 20 out.mp4`.
- Eval: `python lite/evaluate.py [--weights ...]` gives per-difficulty ball accuracy on game10.
- Train: `python lite/train.py [--epochs --batch --boost --name --color]`. It only writes `runs/<name>/last.pt` each epoch, so copy checkpoints yourself if you want to stop early.
- Smoke test: `python lite/train.py --epochs 1 --frac 0.05 --name smoke`, then delete `runs/smoke`.

## Facts that are easy to get wrong
- **Coordinates:** labels and `decode()` outputs are in **1280×720** pixels. The network input is 512×288 and the heatmaps are 256×144. `decode.TO_FULL_RES` = 5.
- **Heatmap channels:** 0 = ball, 1–14 = court keypoints (order = `build_dataset.KP_NAMES` = `demo.COURT_KEYPOINTS`), 15 = player centre, plus a 2-channel size output (w, h in units of `SIZE_NORM` heatmap pixels).
- **Horizontal flip** must also reorder court keypoints (`data.COURT_FLIP`). Forgetting this silently ruins court training.
- **Splits are by match:** val = game9, test = game10. Never split by frame, because neighbouring frames are near-duplicates.
- Court loss is masked by `court.ok`. Unreliable court labels (err > 10 px) must stay masked out.
- Ball labels: `vis` 0 = absent, 1 = clear, 2 = hard to see, 3 = occluded. `status` 0 = flying, 1 = **racket hit**, 2 = bounce.
- **Re-running `fit_court_clips.py` alone overwrites the game4 fix.** Re-run the game4 block of `label_all.sh` afterwards.
- `third_party/TennisCourtDetector` needs `court_detector.patch` (NumPy 2 fixes). It has no licence, so never commit its code or weights.
- A colour model is detected from the weights (`stem.0.weight` has 9 input channels), not from a flag.
- Memory: the 8.8 GB RGB cache combined with 6 DataLoader workers ran the dev Mac out of memory. Lower `--batch` and `num_workers` if you train in colour.

## Current numbers (v2, game10)
Ball F1 0.932 (precision 0.997, recall 0.876); faint balls 57%, racket-hit frames 56%, far court 84%. About 4.8 ms per frame for the model alone on an M2 Max, and about 55 fps for the full demo loop. Known weak spot: small or faint balls get missed, and the model almost never predicts a ball that isn't there. The likely next step is a higher input resolution.
